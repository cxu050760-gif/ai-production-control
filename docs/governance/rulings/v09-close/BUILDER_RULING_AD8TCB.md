## §2 裁定：**AD-8 涵盖 TCB 场景声明**（附四条强制纪律）

**裁定理由（逐条可复核）**：
1. **先例即规范**：冻结的 b2 矩阵夹具（本项目最权威的测量件）自身即
   `set_meta("tcb_status","VERIFIED")` / `authority_status=VERIFIED`
   作为场景构造（`runtime/test_v09_attack_matrix_offline.py:99-100`，
   你引用的先例成立且经主脑复核）。若场景声明 TCB 状态不合法，
   冻结矩阵本身即不合法——它不是。
2. **语义分层**：TCB 验证是**部署态**（生产封印，收口清单第 1 项，
   发布负责人在审查后执行）；测试场景模拟的是一个"已封印的健康世界"。
   二者不同层——**场景声明不是生产封印，也不替代生产封印**。
   你感知的"环依赖"由此消解：9 例转绿不需要等待真实封印。
3. **被测对象不变**：9 例测的是发送路径与出站许可行为，不是 TCB
   验证本身；场景必须让非被测闸门满足，才能行使被测闸门——
   这正是全部离线套件的既有方法论。

**四条纪律**：
1. 声明仅限**场景构造**（per-run state 设置）；不得触碰产品默认值、
   不得触碰闸门逻辑、不得把"声明"写进任何生产路径。
2. **必须补 TCB 闸门负例**（本裁决新增验收件）：经 runtime 发送路径，
   TCB 未验证 → 拒——证明第二道闸门真实存活、未被场景声明架空。
   与 egress 四向负例并列入库。
3. 最终批的 AD-8 登记册必须逐点位列出全部适配
   （`--egress-policy-file` 各调用点 + TCB 声明各调用点），
   每处注明"场景构造，期望未改"。
4. 期望与断言仍然一字不改；任何为翻绿而放宽默认值的做法维持
   HARD STOP（T11B §5.c 继续有效）。
