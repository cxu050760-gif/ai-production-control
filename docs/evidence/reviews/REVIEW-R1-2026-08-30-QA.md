## 发现的缺陷

### DEF-1（REWORK 主因）：bsk 探活端口错误，守护实际失效
- **文件/行号**：`scripts/guard/guard_all.cmd` **L32** `set "BSK_PORT=52900"`（以及 L197-226 `:bsk_check` 探测该端口）
- **证据链**：
  1. `E:\WB\tools\bsk-file-bridge\bsk-home\daemon.json`：`"ws_port": 52800`（bsk 自写权威状态）
  2. `daemon.log.2026-08-30`：`daemon ready, pid=16556, ws_port=52800`
  3. `netstat -ano | findstr :52800` → `TCP 127.0.0.1:52800 ... LISTENING 16556`（bsk-dev）
  4. `netstat -ano | findstr :52900` → **无监听**
- **复现**：`cmd /c guard_all.cmd` → `bsk_check: port 52900 DOWN - starting daemon`（即使 bsk daemon 已在 52800 健康监听）→ 每次运行都误判 bsk 故障并重复 `start bsk-dev.exe daemon start`（daemon lock 单实例所以不翻倍进程，但探活判定恒为 DOWN，账本持续记 ok=false）
- **影响**：①假阴性：bsk daemon 健康时 guard 判 DOWN 并反复 start；②假阳性（更危险）：若 52900 被其他进程（如 playwright-cdp CDP 端口，R2 注册表 browser-playwright-cdp 亦为 52900）监听，guard 会误判 bsk 健康，bsk daemon 实际 DOWN（如 idle 600s 自动退出，daemon.log 16:08:54 实况）时不会及时拉起 → **bsk 回退通道守护失效**
- **修复建议**：`BSK_PORT` 从 `daemon.json` 的 `ws_port` 字段读取（权威），或改为 52800；并上报 production.json `browser.bsk_daemon_port=52900` 配置漂移（该字段已与 daemon 实际不符）

### OBS-2（关联配置漂移，非 R1 脚本引入但需 D 轮统一修正）
`config/production.json` `browser.bsk_daemon_port=52900` 与实际 daemon 52800 不符；R2 注册表 `browser-bsk` health_check port=52900 继承同一假设（R2 审核实测 52900 通系 playwright-cdp 监听，未深究归属）。建议 D 轮统一修正 production.json + registry + guard 三处端口来源。

### OBS-3（审核过程注记——dry-run 方法失误，已自愈）
- 我的 dry-run1 副本（用 LF-only 字符串替换 CRLF 文件的 call 行）替换未生效，意外对生产 watcher/guard 真实执行了 kill+start（33460/29192 → 25828/31288），最终由守护自愈恢复健康。该意外同时**真实验证了判死→杀→重启→心跳恢复全链路**（dryrun 账本 16:05 序列）。dry-run2 采用 CRLF 感知替换后正确屏蔽 kill/start，仅验证判死分支。
- 副作用：bsk daemon 于 16:08:54 因 idle(600s) 自行退出，dry-run2 的 bsk start 分支（未屏蔽）将其拉起（16556@52800）——当前健康。
- 审核全程未触碰 runtime/src/config/docs 正式文件；唯一生产副作用为上述守护自愈行为（与守护设计意图一致）。

### OBS-4（低优先级）
kill_stale 在 16:05 真实执行时账本记 `taskkill failed for one or more stale processes`（ok=false），但后续 start 成功、心跳恢复，守护仍自愈。建议实现者复核 taskkill /F /T 对进程树部分失败的原因（可能子进程已退出导致 errorlevel）。
